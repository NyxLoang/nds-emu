# runner 模块日志

> 职责：把「两台 CPU 交替跑到下一个事件」这件事做成可复用的帧驱动 ——
> 无头模式（`--headless-frames` / `--headless-cycles`）与窗口模式共用同一套
> 调度，并承载所有与「整机时间线」有关的诊断开关（按键注入、截图、热区、
> 低地址直方图等）。源码：`src/runner/runner.c` / `runner.h`。

## 调度模型（现状）

- 系统时钟单位 = 33.513982MHz；一帧 = **560190** 个单位（≈59.8261Hz），
  一扫描线 = `560190/263`（263 行/帧，第 192 行起 VBlank）。
- 两台 CPU 各自累计 `cost9` / `cost7`，系统时间取
  `min(cost9/ARM9_DIV, cost7)`：跑得快的那台多做功，等价于「两台 CPU 并发、
  按各自时钟推进」。
- `timing` 事件表按系统时间挂 VBlank（每帧）与扫描线（每行）；
  两核都在等待时直接跳到下一个事件（21-B9wf 的「等待期时间照常流逝」）。
- 每帧结束补推 SPU（`snd_advance`，32768Hz = 33.51MHz/1024）与 RTC 秒数。
- 21-B9yi：两核都空闲的快进分支里**也要推进卡带时钟**
  （`io_advance_cart(io, 0, delta)`）；否则一笔「数据取完、等软件读走」的
  传输在空闲期永远结束不了，传输完成中断也送不出去。

## 2026-09-12 · 21-B9yi — 帧窗口诊断（ftrace / irqlog / modelog）

- `NDS_FTRACE=LO-HI`：逐帧打印两核 PC/CPSR/IF/IME/IPC FIFO/卡带状态与 DMA3；
- `NDS_IRQLOG=1`：打印每次 ARM9 IRQ 受理（帧、被打断 PC、CPSR、lr、周期数），
  与参考核 `refirq:` 行（`ARM::TriggerIRQ` 内同口径）逐条对照；
- `NDS_MODELOG=1`：打印 ARM9 的每次模式切换（帧、旧→新模式、PC/lr/sp）——
  用于确认「游戏内核在 IRQ 里切任务」这条路径是否与参考核一致。

## 2026-09-12 · 21-B9yg — ARM9 时钟折算对齐参考核（时间线差从 ~240 帧缩到 ~7 帧）

**问题（实测）**：`cost9` 是「ARM9 硬件周期」计数（每条指令 1 个），旧口径
`cost9/2` 把它折算成系统单位，等于让 ARM9 每系统单位跑 2 条指令；而参考核
melonDS 的记账是 **每条 ARM9 指令 ≈ 1 个系统单位**（另有 `MemTimings` 取指
代价）。后果是本地 ARM9 每帧工作量约为参考核的 2.25 倍：

| 观测点 | 本地（旧 ÷2） | 本地（新 ÷1） | 参考核 |
|---|---|---|---|
| 第 8 帧 ARM9 累计指令 | 7,579,029 | — | 3,370,741 |
| 第 26 帧 ARM9 累计指令 | 16,332,769 | 12,065,443 | 8,328,123 |
| 开显示（DISPCNT≠0）帧 | ~13 | 30 | 26 |
| `80111418`（LOGO/加载）帧 | ~13 | ~35 | 43 |
| `00111418` 帧 | ~300 前 | 530 | 539 |
| `00161F10`（标题）帧 | ~300 | 535 | 542 |

**改动**：`runner.c` 引入 `RUNNER_ARM9_DIV`（默认 1，`NDS_ARM9_DIV=2` 可切回
旧口径做 A/B），`cost9` 折算、唤醒补偿、步进判据三处统一使用。

**验证**：

- 逐帧画面对照（`NDS_NOMB=1`，`--shot-every 10` vs 参考核逐帧 dump）：
  **帧 10/20/30 从「第 20 帧起分歧」变成 100% 逐像素相同**；
  帧 50-200 维持 81.9%（与改动前同）；
- 第 1500 帧两边 OCR 都是同一张插图作者画面（`ILLUSTRATION RYOMA ITO`）——
  说明「本地比参考核早/晚一大截」的时间线问题已消除；
- `build\test_nds.exe` **921 项检查 0 失败**；真 ROM 900 帧终点
  `ARM7=00001158`、`disp=00161F10`、`0x027FFC30=0xFFFFFFFF`、
  `0x03808240=1`、`0x0380BA7C=1`（与参考核逐项一致）。

**已知剩余偏差**：本地 ARM9 在第 26 帧仍执行 12.07M 条指令（参考核 8.33M，
多 45%）——melonDS 还会按取指区域加 `MemTimings` 代价（主存 N=8/S=1、
ITCM/IO 等另有基准），本地尚未实现「按区域计费」，属于下一步可选的细化项。

### 21-B9yh 续：取指区域计费落地（非顺序取指加价）

上一节的「剩余偏差」已在 21-B9yh 处理：`cpu.c` 增加
`next_fetch_pc`（顺序取指判据）与 `cpu_fetch_cost()`，**ARM9 主存的非顺序
取指按 3 个单位计费**，其余（ITCM/WRAM/IO/VRAM、以及 ARM7）保持 1。
实测对齐效果：

```
第 26 帧 ARM9 指令：本地 8,138,527  vs 参考核 8,328,123   （−2.3%）
第 1900 帧 ARM9 指令：本地 668,450,486 vs 参考核 720,588,787 （−7.2%）
```

（改前是 +45% / +8.9%；「主存一律 2 单位」的中间方案则是 −15% / −14.2%，
两头都过度惩罚——数据见 [cpulog](../cpu/cpulog.md) 的 21-B9yh。）

**时间线复核**（`--shot-every 10/100` vs 参考核 dump）：

| 观测点 | 参考核 | 本地 | 差 |
|---|---|---|---|
| 开显示（DISPCNT≠0） | 26 | ~27 | +1 |
| `80111418`（加载画面） | 43 | ~54 | +11 |
| `00111418` | 539 | ~550 | +11 |
| `00161F10`（标题） | 542 | ~555 | +13 |

帧 10/20/30/40 与参考核**逐像素 100% 相同**；帧 60-200 保持 81.9%。
可见取指计费修好后，本地的时间线误差从「±240 帧」稳定到 **+1~+13 帧**，
剩余差集中在加载/过场这类「等 IO 完成」的阶段（下一步可查卡带/DMA 完成时刻）。

### 21-B9yi（续12）— `NDS_FTRACE` 补 IE 与卡带 FIFO 状态；2600 帧行为对照

- 每帧行新增 `ie9/ie7`（此前只有 `if9/if7` 与 `ime`）：卡带中断挂错核这类问题
  一眼可见（修复前后本地 `if7` 从恒挂 `00080000` 变成 `00000000`）。
- 卡带行新增 `fifo=<data_count> late=<data_late>`：用来分辨「卡带还在取数」
  （`wait_phase=1`）与「FIFO 满、等 CPU/DMA 读走」（`late=1`）两种停摆。
- `--dump <前缀>` 与 `--shot <文件>` 继续作为里程碑取证（本轮 900/2600 帧）。

**行为对照（必须带按键时序）**：

| 观测点 | 21-B9yi 基线 | 本轮改后 | 参考核 |
|---|---|---|---|
| 带按键 f=2000/2600 | `0200957C`（空闲任务，不醒） | `02011C50`（IRQ 模式、芯片 ID 读取路径等 bit31） | 继续执行（ITCM/main RAM 之间正常切换） |
| 帧 100 画面 | 81.9% | **81.9%**（无回归） | — |
| 900 帧里程碑三标记 | 一致 | **一致** | 0xFFFFFFFF / 1 / 1 |

> ⚠️ 不带 `--key-frame` 的长跑会停在标题/演示（attract）循环，本地会「看起来在推进」
> （DISPCNT 每 5 帧翻转、ITCM 逐字节 0.00%）。那不是 START 之后的进度，
> **停摆判定与内存对照一律用带按键时序的运行**。

> ⚠️ `--dump <前缀>` 与 `--key-*` 同时使用、且 `--dump` 写在参数**末尾**时，Windows
> 宽字符参数解析可能把前缀吃掉（文件落到当前目录、名字退化成 `_mainram.bin`）。
> 把 `--dump` 放前面即可（如 `--dump build\p_ --key-frame 1700 … --headless-frames N`）。

## 2026-09-12 · 21-B9yi（续32）`--stats-every N`：画面统计诊断

- **做了什么**：无头帧驱动里新增 `--stats-every N`（`runner_set_stats_series()`）：
  每 N 帧用 `render_frame()` 出两块 256×192 图，打印
  `stats: f=… top nz=<非黑像素>/<总数> rgb=<均值> bot …`。
  口径（非黑 = 三通道不同时为 0、均值按全屏像素计）与参考核 harness 新增的
  `REF_STATS_EVERY` **完全一致**，用于客观回答「某段画面是定格还是持续在变」。
- **怎么验证**：本地 9000 帧、参考核 9000 帧同输入脚本各跑一遍，逐 100 帧对比
  （`build\local9000.txt` / `build\ref9000.txt`）；另用 `NDS_NOMB=1` 复核
  MASTER_BRIGHT 是否影响统计口径。
- **结果**：✅ 可用。附带结论：f=7200-7600 两边都进入「画面长时间不变」的等待态
  （本地顶屏非黑 9.8%、参考核 100%，差异来自 3D 纹理未实现，见 gxlog 续32/33）。

## 2026-09-13 · 21-B9yi（续41）：性能——把「每指令热点 PC 统计」从热路径摘掉

- **做了什么**：`runner_step()` 此前**每条 ARM9 指令**都更新热点 PC 直方图
  （`s_h9_pc[65536]` 随机写 + `s_h9_cnt` 计数 + 总数），这是纯诊断设施却跑在最热路径上
  （`s_h9_cnt` 是 512KB 数组）。改为仅在 `NDS_PCHOT=1` 时统计，默认关闭；
  同时把 `cpu_step()` 里四个 `if (diag)` 诊断分支合并成一次判断。
- **怎么验证**：同机交替 A/B（各 2 次 4200 帧、同输入脚本、同一台机器）：
  ```
  配对 1： 含热图 222.6s (18.9fps)  →  关热图 175.9s (23.9fps)   -21%
  配对 2： 含热图 135.6s (31.0fps)  →  关热图 133.1s (31.6fps)   -1.9%
  ```
  ⚠️ 同一二进制在两次运行间会从 135s 漂到 222s（机器自身 1.6 倍波动），
  所以只能看**相邻配对**的差值，不能跨时段比较绝对值。
- **结果**：✅ 保留（零语义风险的纯删减工作量）；单测 931 项 0 失败。
另记录两个**零收益**实验供后续参考：LTO（`-flto`，配对差 1%——⚠️ 见 `src/cpu/cpulog.md`
续62 的更正：那次对比的两个构建**都没真正开 LTO**，续62 修好 CMake 的 IPO 探测后
LTO 实测 **-13.2%**）、
  访存监视快速路径（`watch_on`，配对差 0.2%）。

## 2026-09-13 · 21-B9yi（续67）：**拖拽手势注入** `--touch-drag X1,Y1,X2,Y2`

- **动机**：窗口鼠标本来就能拖拽，但无头脚本只能「点一下」，没法自动验证
  「从单位拖到目标点」这类手势（战斗里下指令就是这种）。
- **做了什么**：
  ```
  --touch-frame F --touch-drag X1,Y1,X2,Y2 [--touch-drag-steps N] [--touch-period P]
  ```
  到第 F 帧按下，随后**按帧**沿直线分 N 帧（默认 12）移动到目标点，再抬起；
  `--touch-period P` 可周期重复。坐标与 `--touch-*` 同为底屏像素。
- **踩到的坑（值得记）**：`runner_touch()` 是**每条指令**调用一次（不是每帧），
  第一版按调用次数推进步进，结果 N 步在**同一帧内**瞬间走完 ——
  游戏只看到「按下又立刻抬起」，完全无响应（实测与不触摸逐字节相同）。
  改用 `runner_frame_index()` 判断「过了几帧」后才正常。
- **怎么验证**：
  ```
  早期画面（已知会响应触摸）3000 帧对照：
    无触摸          ：f=500 顶屏 rgb=122,92,58（有画面）
    单次拖拽(f=100) ：与无触摸逐字节相同 ← 单次触发会错过时机
    重复拖拽(每200帧)：f=500 变黑、f=1000 rgb=198,190,192 ⇒ **拖拽确实送达游戏**
  战斗界面（f=12000 起每 200 帧一次拖拽，20000 帧对照）：
    最终截图哈希相同，但 ARM7 IRQ 254936 vs 254934、IE 位与定时器诊断出现
    776 行差异 ⇒ **触摸扰动到了游戏逻辑**，但该状态没产生可见的部队指令
    （脚本长按全键，游戏多半停在 HUD/自动演出相位）
  ```
- **结果**：✅ 保留（工具可用）；同时留下「战斗内下指令需人工试玩确认」的开放项。

## 2026-09-13 · 21-B9yi（续71）：**随机输入浸泡** `--key-random` / `--touch-random`

- **动机**：固定脚本只能走游戏的一条固定路径。「这条路上没有未实现的东西」
  不等于「游戏没被实现的路径不存在」——需要**随机输入**去撞（模拟器常见的 soak 测试）。
- **做了什么**：
  ```
  --key-random SEED   [--key-period P]    每次触发用种子 LCG 取一个随机键掩码（bit0-11）
  --touch-random SEED [--touch-period P]  每次触发在底屏随机位置（0..255 × 0..191）按一下
  ```
  语义与原有脚本一致（按下保持 12 帧），窗口路径同样支持。
- **怎么验证 / 结果**（40000 帧、随机按键每 40 帧 + 随机触摸每 60 帧）：
  ```
  无崩溃、无停摆（f=5000…40000 各采样点两屏均有内容；f=20000 底屏黑是过场淡出）
  未知 IO 地址种类：**139 种，与固定脚本 40000 帧那次完全相同（零新增）**
  SWI 诊断：0x03/0x06/0x0B/0x0E —— 与固定脚本相同，全部已实现
  未实现指令/异常提示：无
  ```
  ⇒ **随机输入走不到任何未实现路径**，这是目前对「实现完整度」最强的一次反证式验证。
- **结果**：✅ 保留（工具）。

## 2026-09-13 · 21-B9yi（续75）：**画面指纹** `--screen-hash-every N` —— 客观的「进度刻度」

- **动机**：判断「游戏被带到多远」需要一个客观刻度。`disp-change` 太粗（只反映显示寄存器
  组合，随机输入 40000 帧也只多出 1 种），逐帧截图又太重。
- **做了什么**：每 N 帧渲染一次双屏，各算一个 64 位 FNV-1a 哈希并打印
  `screenhash: f=… top=… bot=…`；统计**不同哈希个数** = 这段运行「跑过多少张不同画面」。
  只在指定 `--screen-hash-every` 时才渲染（默认零开销）。
- **结果（同长度、同会话并行，20000 帧 / 80 个采集点）**：
  ```
  A 固定脚本（--key-frame 1 --key-mask 0x3FF --key-period 120）：不同画面 35 张
  B 自然输入（--key-random 12345 --key-period 40 + --touch-random 999）：不同画面 **61 张**
    summary 也完全不同：A vram-nz=187225 / B **vram-nz=393216（整块 VRAM 被写入）**
  ```
  ⇒ 自然输入能把游戏**带到远得多的地方**（61 vs 35 张画面、整块 VRAM 被填满）。
  这同时说明：**「按住全键」这种脚本会显著限制游戏推进**，以后做长跑/进度对照
  一律以自然输入为准。

## 2026-09-13 · 21-B9yi（续78）：交互扫描 —— 用指纹分叉自动定位可交互 UI

- **方法**（不需要新工具，利用确定性）：同脚本两组，一组不注入触摸、一组从 f=12000 起
  每 100 帧随机位置轻触；两组都 `--screen-hash-every 15` 采指纹。**f<12000 输入完全相同
  ⇒ 指纹必须逐帧一致（自带对照）**；之后的分叉即「轻触造成了可见反应」。
- **结果**：
  ```
  f<12000：0 处分叉（自检通过）        f≥12000：192 处分叉，首处在 **f=12240**
  注入序列（seed 777）：f=12000(176,69) → f=12100(102,161) → **f=12200(21,190)**
  ⇒ 首次可见反应来自 f=12200 在 (21,190) 的轻触 = 战斗界面左下角 LEADER 面板
  f=12260 两张截图对比：顶屏差 46,560/49,152 像素（95%，3D 视角整幅改变）、底屏差 212 像素
  ```
- **结论**：✅ 方法可复用（同脚本 + 指纹逐帧对照 + 前段零分叉自检），
  将来自动走菜单/找按钮都可以照这个套路做；本次也直接证明了触摸能**操作游戏 UI**。

## 2026-09-13 · 21-B9yi（续79）：**单次轻触二分** —— 更正归因，并发现「需要连续交互」

- **为什么做**：续78 只看到「首处分叉 f=12240」，但那**不等于**就是最近那次轻触造成的；
  要定因果，必须让两组输入**只差一次轻触**。
- **做法**：对注入序列里的每一次轻触各跑一组（`--touch-period 0`，只按一次，
  保持 12 帧），其余输入（`--key-random 12345 --key-period 40`）与基线完全相同，
  各跑到 f=12600，再与无触摸基线**逐帧比对指纹**。
- **结果**：
  ```
  T1 (176,69) @12000 → 0 分叉      T2 (102,161)@12100 → 0 分叉
  T3 (21,190) @12200 → 0 分叉      T4 (42,121) @12300 → 1 分叉（f=12450）
  对照：连续轻触（每 100 帧）→ 192 分叉（首处 f=12240）
  ```
- **结论**：①**更正**——单次轻触常常没有可见效果，「首处分叉」不能直接归因给最近那次；
  ②**新认识**——该触摸 UI 需要**连续/重复交互**（或必须点在激活元素上）才生效；
  ③方法学——**单次轻触二分**是有效的因果定位手段，输入类结论应先做它。
