# snd 模块日志

> 覆盖：NDS 音频（16 通道 + 混音器）。`src/snd/snd.h/.c` 纯核心实现（不依赖 SDL），
> 按地址提供 16 通道寄存器（`SOUNDxCNT/SAD/TMR/PNT/LEN`）与主控（`SOUNDCNT/SOUNDBIAS`），
> `snd_render` 合成 32768Hz 立体声样本，供 SDL 回调（`main.c`）或测试直接断言。
> 寄存器地址落在 IO 区（`0x04000400..0x04000505`），由 `io_read8/io_write8` 转发到本模块。

## 18.1 — 短文 + 头文件

- **做了什么**：新增 `docs/19-audio.md`：16 硬件通道（PCM8/PCM16/IMA-ADPCM/PSG）、
  各通道寄存器布局、`SOUNDCNT/SOUNDBIAS` 主控、混音流程与采样率计算。

- **怎么验证**：`test_snd_regs` 写读回 SOUNDCNT/SOUNDBIAS + 通道 0/1 全套寄存器 + 越界读 0。

## 18.3 — 混音器

- **做了什么**：`snd_render(snd, bus, out_l, out_r, n)` 每采样遍历 16 通道，按格式解码：
  - **PCM8**：`(int8)byte << 2`；**PCM16**：`(int16)half >> 6`（都折到 10 位有符号域 ±0x200）。
  - **IMA-ADPCM**：首读头字（bit0-6 7 位有符号初始采样 `<<9`、bit8-15 步进索引），之后每个 4 字节数据字
    拆 8 个 4-bit nibble 依 IMA 步进表（`7..31`）与索引表解码；追赶游标保证按需解码。
  - **PSG**：方波（通道 8-13，8 步 × 占空比 duty+1）与白噪声（通道 14-15，确定性伪随机）满幅 ±0x200。
  - 音量（mul/127 ÷ 除法器 1/2/4/16）→ 声相（pan 0..127 分左右）→ 主音量（SOUNDCNT bit0-6）→
    加偏置（SOUNDBIAS bit0-9）并夹到 10 位 → 输出 16 位。
  - 游标定点 16.16 推进（`inc = master_clock<<16 / tmr / mix_rate`，tmr=0 视作 65536）；单发/手动到总长停 bit31，
    循环回绕（简化：回绕从头重放，PNT 循环点暂不实现）。
- **踩坑修复**：ADPCM 头初始采样符号扩展原为 `if (init>=0x4000) init-=0x8000`，对 7 位符号位（bit6）错位；
  改为 `if (init&0x8000) init-=0x10000`；游标越界比较用 `uint64_t` 防大长度 `<<16` 溢出。
- **怎么验证**：`test_snd_mix`（PCM8/PCM16/ADPCM/PSG 样本值 + 静音 + 主音量 0 + 单发停止）全过。

## 2026-09-12 · 21-B9wu — 无头模式按帧推进 SPU（游戏轮询播放状态不再死等）

- **证据**：FFXII 开场后 ARM7 的热点代码是 `0x037FEFD0-0x037FEFE8`
  （`ldrb r0,[0x04000403+idx*16]` → 取 SOUNDxCNT 高字节的通道状态位并轮询）。
  窗口模式下 SDL 音频回调会按实时速率调用 `snd_render` 推进通道游标；
  **无头模式没有回调**，通道永远停在 `start` 位，游戏就在这个轮询里出不来。
- **修复**：`snd_advance(snd,bus,samples)` 按“经过的样本数”渲染并丢弃结果，
  只推进通道游标/结束标志；`snd_set_host_render_active()` 让 audio.c 在打开
  SDL 设备时置位，runner 每帧在**没有宿主回调**时按 `tm.now/1024` 补推
  （NDS 32768Hz = 33.51MHz ÷ 1024）。
- 新增 `[case 21-B9wu]`：PCM8 单发通道 → `snd_advance(2048)` 后 start 位清零。

## 2026-09-12 · 21-B9xi — SOUNDBIAS 复位值与 10 位写语义

- **证据**：参考核 IO 快照（帧 1500/1900/2200）里 `0x04000504` 都读回 `0200`，
  本地是 `0000`；melonDS 侧该寄存器是 10 位、`Bias = val & 0x3FF`，
  混音公式 `(bias<<6)-0x8000` 在 `bias=0x200` 时正好抵消为 0。
- **修复**：新增 `snd_reset()`（通道清零 + `soundbias=0x200`，真机上电值，
  `io_create` 调用）；低字节写不再把高 2 位混进低字节（旧实现 `val & 0x03`
  会丢掉 bit2-7），高字节只保留 bit0-1，读回统一按 10 位掩码。
- **效果**：`--dump` 的 io7 快照 `SOUNDBIAS=0200` 与参考核一致。

## 2026-09-13 · 21-B9yi（续86）：与参考核**同帧段音频对照** —— 时间轴对齐，但音量口径不同（开放项）

**做了什么**：给参考核 harness 加 `REF_WAV=路径`（`SPU::SetOutputSampleRate(32768)` +
每帧 `SPU::ReadOutput()` 流式写 WAV），与本地 `--snd-wav` 做同脚本对照
（`--headless-frames 2000 --key-frame 1 --key-mask 0x3FF --key-period 120`）。

**结果**（逐秒 RMS，本地 vs 参考）：

```
t=0–4s   两边都静音（开机）                        ← 对齐
t=5–11s  本地 29/614/1906/3362/27/0/0   参考 4508/3180/6440/4164/3655/3052/222   ← 明显不同
t=12–13s 两边都静音（换场）                        ← 对齐
t=14s+   两边都有内容，但参考普遍更大：本地 1166–4187 vs 参考 1337–6770
逐秒 RMS 相关系数 0.528；本地最大值/参考最大值 ≈ 0.62
```

**怎么解释（诚实边界）**：

1. **时间轴结构对得上**（开机静音段、t=12–13 的换场静音段两边一致）⇒ 采样率、单帧样本数
   （本地 548/帧、参考 2191/帧 但同为 32768Hz 时间轴）、SPU 推进时机基本正确；
2. **音量口径不同**（本地整体约 0.62×）；而且 t=5–11 段差异很大；
3. **不能直接归因给 SPU**：这个参考核是 melonDS **master**，续29 已证明它与本地在
   `f≥40` 就视频分叉 ⇒ 两边**可能根本不在同一游戏状态**，那段「本地安静、参考有音乐」
   也可能只是场景不同。要做严格结论，需要续29 里那条「找回历史参考核」的路。

**已定位的代码级口径差异**（读参考核源码得到，不依赖上面的输出对照）：

| 环节 | 参考核（melonDS `SPU.cpp`/`SPU.h`） | 本地当前 |
|------|--------------------------------------|----------|
| 通道音量 | `Volume = Cnt & 0x7F; if (==127) ++`（127→**128**） | `raw * mul / 127`（127→127） |
| 音量除法器 | `volshift[4] = {4,3,2,0}`，语义是 `val <<= shift`（末尾再统一右移） | `div_shift[4] = {0,1,2,4}` 直接除 |

> **21-B9yi（续88）更正**：上表初稿把这一行写成「映射相反」，**是错的**。
> 复核：两边都是 `bits=0` 最响、`bits=3` 最轻（响度比同为 16 倍），只是表达方式不同。
> 并且把整条链在满音量/满声像下解析展开，**两边输出完全相同**（PCM8/PCM16/ADPCM 三条都算过）
> ⇒ 前面测到的 0.62× 音量差**不是**增益链造成的（更可能是两边游戏状态不同 / PSG 表差异）。
| 声像 | `Pan=(Cnt>>16)&0x7F; if(==127)++`；`left += (in*(128-Pan))>>10` | `v*(127-pan)/127`（缺 +1、用除法而非 >>10） |
| 主音量 | `(sum * MasterVolume) >> 7`（127→128） | `mix * master / 127` |
| 输出定标 | `>>= 8`，**掩码**降 10 位（`&= 0xFFC0`） | 把混音**钳位**到 `0..0x3FF` 再 `<<6`（硬限幅语义） |
| 偏置 | `out += (Bias<<6) - 0x8000`（Bias=0x200 → 0） | `clamp(mix + bias, 0, 0x3FF)` 后 `-0x200 <<6` |

**结论 / 下一步**：本地混音链是「自定口径」，与参考核逐环节都不同；**「混音增益链对齐参考核」
列为待做的保真度项**（改动会牵动阶段 18 的单测期望值，需要一起更新）。本轮只记录差异，
不改实现 —— 因为当前还没有可信的同状态对照（master 参考核与本地已分叉）。

## 2026-09-13 · 21-B9yi（续88）：PSG 表 / 噪声 LFSR 换成参考核口径 + **游戏用格式普查**

- **先更正**：续86 的「6 处口径差异」里，**音量除法器「映射相反」是错的**（见上文更正框）。
  把两边的链在满音量/满声像下解析展开后**输出完全相同** ⇒ 增益链不是音量差的来源。
  真正剩下的差异只有两处：**PSG 波形表**与**输出末级（钳位 vs 掩码，未触顶时等价）**。
- **做了什么**（`src/snd/snd.c`，全部按 melonDS `SPU.cpp`/`SPU.h` 抄）：
  1. **PSG 方波表**：换成参考核的 `PSGTable[8][8]`（±0x7FFF，`duty=0` 首样本为**负**），
     索引 `[(Cnt>>24)&7][Pos&7]`；本地原来是「自定相位 + 占空比 (duty+1)/8」。
     量纲转换：参考核 16 位 → 本地混音 10 位域，统一 `>>6`；
  2. **噪声 LFSR**：`NoiseVal` 初值 0x7FFF，每一步「先看最低位决定输出 ±0x7FFF，再
     `>>1 ^ 0x6000`」；本地原来是「`idx*常数` 取位」的自定伪随机。通道 14/15 的 PSG 格式
     = 噪声（参考核 `DoNum >= 14 → Run<4>` 同口径）；
  3. 顺带补**诊断**：跑完打印 `sndch: starts/ends …`（每通道启动/结束次数）与
     （`NDS_SNDSTAT=1` 时）`sndfmt: pcm8/pcm16/adpcm/psg/noise` 的**样本数普查**——
     回答「这处改动到底对这个游戏有没有影响」。
- **验证**：
  ```
  单测 952 项 0 失败（新增 5 项：duty0 首样本=负满偏、duty0 第 8 样本=正满偏、
                       duty7 全负、噪声前两样本、以及噪声 LFSR 状态推进）
  锚点 2000 帧：截图 SHA-256 仍 A72E11A2…CC513（视频零回归）
                WAV 哈希与改动前**完全相同**（38B1D1F5…6360）⇒ 该窗口没用到 PSG/噪声
  20000 帧自然输入 + NDS_SNDSTAT（**游戏用格式普查**）：
    sndch:  16 个通道全部在用（各启动 384~644 次）
    sndfmt: adpcm=157,036,977  pcm16=3,148,335  pcm8=167,400  psg=0  noise=196,940
    ⇒ 音乐/语音几乎全是 **ADPCM（99.5%）**；**方波 PSG 一次都没用**（0 样本）；
      **噪声通道用了约 19.7 万个样本（≈6 秒音效）** ⇒ 噪声 LFSR 这处改动**真的生效**，
      PSG 表这处是「正确但对本作不触发」（保留，作为学习与泛化正确性）。
  ```
- **结论**：✅ 保留。至此「声音」这条线有：设备打开（续42）→ 混音非静音（续60）→
  可听可复现（续85）→ 与参考核同帧段对照（续86，含一处**已更正**的结论）→
  **格式普查 + 波形源按参考核口径**（本轮）。

## 2026-09-13 · 21-B9yi（续89）：**ADPCM 解码按硬件重写**（本作 99.5% 的音频样本都走这条路径）

- **动机**：续88 的格式普查显示 `adpcm=157,036,977 / pcm16=3,148,335 / pcm8=167,400`，
  即**音频主体是 ADPCM**；于是把本地解码器逐行对参考核 `SPUChannel::NextSample_ADPCM` 复核。
- **查出三处与硬件不符**（都是真错误，不是风格差异）：
  | 项 | 硬件/参考核 | 本地原来 |
  |---|---|---|
  | 头部位布局 | bits0-15 = **16 位**初始采样、bits16-22 = 初始 index(0..88) | `(hdr&0x7F)<<9` 取 7 位采样、`(hdr>>8)&0xF` 取 index |
  | 步进表 | **89 项** IMA 表（7 … 0x7FFF） | 16 项小表（7…31），index 夹在 0..15 |
  | nibble 顺序 | 数据从 SAD+4 起、**每字节低 nibble 在前**；前 8 个源采样是热身（输出 0） | 32 位字内 **MSB-first** 取 nibble，无热身 |
- **做了什么**：按参考核口径整段重写 `snd.c` 的 ADPCM 部分（89 项表 + `{ -1,-1,-1,-1,2,4,6,8 }`
  索引表 + 逐字节低 nibble 优先 + 8 样本热身 + 夹在 ±0x7FFF）。
- **验证（这条改动是**可听**的）**：
  ```
  单测 953 项 0 失败（ADPCM 用例改成参考核语义：热身样本=0、第 9 样本 = 负满偏 0x8000）
  视频锚点：2000 帧截图 SHA-256 仍 A72E11A2…CC513（音频改动不影响视频）
  音频**与参考核逐秒对照**（同脚本 2000 帧，RMS 单位）：
            t=28..32 秒：旧 952/123/140/236/79  →  新 4539/4019/3208/3806/4288（参考核 5946/6292/6015/5331/5301）
            旧版「参考核在放音乐、本地几乎无声」的那一段**修好了**
            逐秒 RMS 相关系数：**0.528 → 0.748**；后半段音量比从约 0.3~0.7 提升到约 0.85
  WAV 哈希从 38B1D1F5…6360 变成 C8075464…1501（解码结果确实变了，旧的是错的）
  试听片段已用新解码重录：docs/audio/ffxii_2000f_t12_24s.wav（哈希 F286EB53…DB46F）
  ```
- **结论**：✅ 保留。**这是「声音」线上第一个真正可听的保真度修复**——
  之前 99.5% 的音频样本都用错了步进表与位布局。
