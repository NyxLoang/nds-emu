## 2026-09-13 · 21-B9yi（续96）：即时存档 / 读档（第一版）

- **做了什么**：
  - 新模块 `src/state/`：`state_save()` / `state_load()`。
  - **存什么**：Main RAM(4MB)、ARM9 ITCM(32KB)/DTCM(16KB)、ARM7 WRAM(64KB)、
    Shared WRAM(32KB)、VRAM(656KB)、调色板(2KB)、OAM(2KB)、两颗 CPU 的全部寄存器/
    CPSR/SPSR/模式/周期计数/CP15、IO 寄存器区（中断/定时器/按键/DMA/FIFO/同步/显示/
    触摸/存储控制/电源/数学/音频/GX/卡带总线）、存档芯片内容，以及**宿主调度时间戳**
    （runner 的 `tm.now` 与两颗 CPU 的周期预算——只靠 CPU 指令计数不够：时间轴单位是
    系统时钟，`cpu->cycles` 是指令条数）。
  - **不存什么**：ROM（只读）、宿主侧（SDL 窗口/纹理/菜单）、各结构里的**指针**
    （`bus->io`、`cpu->nds`、`io->bus`、`gx.bus`、`cartbus.rom`、`save.data`）——
    读档时保留当前对象的指针，只覆盖数据字段。
  - 文件格式：8 字节 magic + 版本 + 帧号 + ROM 大小 + 存档芯片大小 + 宿主时间戳 +
    各块数据 + FNV-1a 校验和；ROM/芯片大小不符或校验失败都会拒绝读入。
  - 接线：CLI `--load-state PATH` / `--save-state PATH` [+ `--state-save-frame N`]；
    窗口热键 **F5 存 / F8 读**。读档后 `runner_resync_time()` 把调度时间轴、输入脚本
    相位、CPU 等待标志一起拉回存档时刻。
- **怎么验证**：
  ```
  单测 961 → 976 项 0 失败（新增 15 项）：保存→改乱→读回，主存/VRAM/ARM7WRAM/
  CPU9 的 r0 与 PC/CPU7 的 r3/周期计数/存档芯片/帧号全部复原，且 bus→io→cpu 的
  反指指针完好（读档后还能正常访存）。
  端到端：跑到第 300 帧存档、继续跑到 500 帧；另起一次从该存档读入再跑 200 帧。
  ```
- **结果**：✅ 保留（可玩用）。**已知限制（诚实记录）**：端到端**不是逐字节延续**——

  ```
  A（跑 500 帧，第 300 帧存档） vs B（读档 + 200 帧）
  帧 301 / 310 的**画面与双屏统计完全一致**（截图 SHA-256 相同）
  但 ARM7 的周期预算从第一帧起就差 10（536127 vs 536117），
  随后每帧累积（302 帧差 20、303 帧差 30、304 帧差 17057…）⇒ 约百帧后走到不同场景
  ```

  已用 `NDS_STATEDBG=1` 逐项排除：存档/读档瞬间的 CPSR、IME/IE/IF、`timer_on`、
  卡带时钟**两侧完全一致**；输入脚本相位、CPU 等待标志、宿主时间戳都已按存档复原。
  剩余差异怀疑来自 ARM7 侧某个更细的时序状态（音频/定时器子周期的衔接），
  属于下一步的深挖点。**结论：存档状态可以正常继续游玩，但不能当作「逐字节重放」用。**

## 2026-09-13 · 21-B9yi（续97）：把「读档后不逐字节延续」追到**指令级**

- **新增工具（都在 `runner.c`，用环境变量开）**：
  * `NDS_TRACE_FRAME=N` + `NDS_TRACE_COUNT=K`：从第 N 帧起逐条打印 K 条指令
    （谁跑的 / PC / r0-r3,r7 / sp / lr / CPSR / 指令计数 / **IF9/IF7** / 调度时间 `now` /
    **ARM7 timer0/timer1 的 cnt_l/cnt_h/acc**）。用来 diff「本该一致的两条时间线」。
  * `NDS_STATEDBG=1`：存档/读档瞬间打印 CPSR、IME/IE/IF、timer_on、卡带时钟。
- **怎么用**（就是本轮的做法）：
  ```
  A：跑到第 300 帧存档、继续跑 → 抓 trace（起点设成第 300 帧）
  B：读该档、跑同样步数     → 抓同样长度的 trace
  diff 两个 trace：第 i 行不同 ⇒ 分歧就在那条指令
  ```
- **本轮的定位结果**：前 **63,817 条指令逐字段完全相同**（PC/寄存器/CPSR/指令计数/
  调度时间/定时器内部状态全同），第 63,818 条开始不同：
  ```
  now=168116640  两侧 CPU 状态与 timer 状态完全相同
                 A: if7=00000004（ARM7 timer0 中断置位）→ ARM7 跳 IRQ 向量 pc=00000018, cpsr=800000D2
                 B: if7=00000000（没有置位）→ ARM9 继续执行
  t70=0648/00C1/63  t71=FB80/00C1/62   ← 两侧逐值相同（cnt_l/cnt_h/acc）
  ```
  ⇒ 分歧点是一处**时间近似同一刻、状态相同、但一侧没置 IF** 的定时器/中断调度差异。
  结合 runner 的调度口径（`io_advance_timers` 只在该核 `was*`（等待）时推进、
  用 `delta = tm.now - last_now` 计费），最可疑的是读档后 **`last_now` 与定时器的
  计费相位**没有完全对齐（差一个很小的时间片就足以让「此刻是否跨过 reload」翻转）。
- **结论**：存档状态**可以正常游玩**，但不能当作「逐字节重放」；分歧点已经精确到**一条指令**，
  下一步沿着「读档后 `last_now`/定时器计费相位」这条线继续即可（工具已就绪）。

### 续98 追记：定时器计费口径不是读档分歧的原因

续98 把 runner 的定时器推进口径做了 A/B（门控 vs 按系统时间无条件推进两个核，
开关 `NDS_TIMER_ALL=1`）：两种口径下「与参考核的内存吻合度」和「分叉帧位置」**逐值相同**，
说明续97 定位到的那条「IF 没置位」的分歧**不是**定时器计费口径造成的。
⇒ 读档分歧的下一步应沿「读档后 `last_now` 与**调度器等待标志**的衔接」继续查（工具已就绪）。

## 2026-09-13 · 21-B9yi（续100）：补两处**真实遗漏**（GX 静态状态、runner 等待标志）+ 剩余分歧的盲区

- **查法**：续97 用指令级 trace 把读档分歧定位到「同一时刻、状态全同、只有 ARM7 timer0 的 IF 位
  一侧置位」；本轮先怀疑 runner 的定时器门控（续98 已排除），再逐个**排查「没进存档的状态」**。
- **补上的两处真实遗漏**：
  1. **GX 的文件级静态状态**（`src/gx/gx.c` 里的 `g_q/g_q_head/g_q_len/g_pending/g_ent/g_e_head/g_e_len/g_need/g_ccmd`）：
     它们是 GX 命令队列与解析后的条目流，**不是 `gx_t` 的成员**，此前完全没进存档 ⇒
     读档后 GPU 侧状态与存档时刻不一致。新增 `gx_state_size/save/load()`（全是定长数组、无指针），
     state 模块把它作为一个带长度前缀的块写入/读回。
  2. **runner 的等待标志** `a9_wait/a7_wait`：它们是「该核是否在 WFI/挂起」的调度状态，
     直接决定读档后**定时器是否继续走**（runner 只在核处于等待时推进它那一侧的定时器）。
     此前是用 `step_cycles==0` 猜的，现在通过 `state_set_host_wait/get_host_wait` **直接存进档**。
- **核对**（`NDS_STATEDBG=1` 现在会打印 ARM7 两个定时器的**全部字段**）：
  ```
  存取两侧逐字段一致：t70 cnt_l=02A5 cnt_h=00C1 reload=0000 acc=9
                      t71 cnt_l=F7DD cnt_h=00C1 reload=F7DB acc=8
  默认路径零回归：锚点 2000 帧截图仍 A72E11A2…CC513、单测 976 项 0 失败
  ```
- **剩余分歧（未解决，但有明确盲区）**：读档后仍然不是逐字节延续。指令级 trace 显示
  **第一处不同只有 runner 的等待标志**（A：`w7=0` 且 `if7=00000004`；B：`w7=1` 且 `if7=0`），
  而 CPU/时间/定时器可见状态都逐字段相同。**关键盲区**：`runner_step` 里
  「**两个核都在等待**」的那条分支（推进到下一个定时事件、推进两侧定时器、处理按键脚本）
  **没有 trace 打点** ⇒ 两组 trace 「看起来相同」，但该分支内部仍可能不同。
  下一步应给那条分支也加 trace（或在里面记录 `timing_next` 的落点）再 diff。

### 续100b：给「两核都在等待」分支补 trace 之后，分歧点**没变**——但形态更清楚了

- 给 `runner_step` 里那条**唯一没打点**的分支（两个核都在等待 → 推进到下一个定时事件、
  推进两侧定时器、处理按键脚本）也加了 trace（`tr idle now=… delta=… if9/if7/定时器`）。
- 重新 diff：**首处不同仍在第 63817 条**，且形态不变 —— 两侧 CPU/时间/可见定时器状态全同，
  唯一差别是 **runner 的等待标志 `w7`**（A=0，B=1）与之对应的 **`if7` bit2**（A=4，B=0）。
- 顺着唤醒条件看：`RUNNER_WAKE7_IO = (ie & ifl) != 0`，`ie7=0104009D` 含 bit2 ⇒
  **A 的 ARM7 被 timer0 中断唤醒并去跑 handler；B 的 ARM7 继续挂起**。
- 关键推理：两侧定时器**可见计数器与小数累加器相同**，但 A 触发了额外的溢出 ⇒
  A 的 timer0 **多走了一个整周期**（t70 的 `reload=0`，div=64 ⇒ 一个周期 = 65536×64
  ≈ 4.19M 系统周期 ≈ 125 ms），即 B 侧的定时器推进**累计少了约一个周期**的量。
  下一步应沿「周期级累计差」查：把 `timer_advance` 的**每次调用参数（idx/cycles）**
  也记录进 trace，diff 到第一次出现差额的那次调用。
